# Better retrieval did not change which jobs GigBid would bid on

GigBid starts with a practical question for a freelancer. Does this job make sense for me, and what can I honestly say about my experience? The workflow reads the job, checks for risks, searches portfolio evidence and proposes a price. If the job passes those checks, it drafts a cover letter and screening answers. The freelancer reviews the draft and its citations before approving an outgoing action. I expected that improving the portfolio search would also improve the bid decision. The experiment exposed a different bottleneck.

## The retrieval change worked

I compared dense retrieval, lexical search, hybrid search, query decomposition, reranking, outcome-aware ranking and corrective retrieval on a labelled synthetic development set. The set contained 51 jobs across full-stack, data analysis and AI and ML personas. Forty-two jobs had graded evidence. The remaining jobs were useful for observing whether the system could refrain from returning passages when the portfolio offered no match. I measured the retrieval results against the evidence labels before looking at any downstream proposal outcome.

The dense baseline, V0, ranked portfolio passages by embedding similarity. V2 combined dense results with BM25 using reciprocal rank fusion. That fusion gives passages credit for ranking well in either list and lets results that both methods favor rise to the top. The hybrid approach can find a specific tool name through lexical matching and a relevant description through semantic similarity. On this dataset, Recall at five rose from 0.630 to 0.752, while nDCG at ten rose from 0.763 to 0.812. V2 led the dense baseline on each persona. Removing the hybrid component reduced nDCG by about 0.049. [Retrieval results](../evals/results/retrieval-20261109-111100.json)

The more elaborate variants told a less tidy story. Cross-encoder reranking added seconds of CPU work per query and did not improve the aggregate scores here. The portfolio collections were small enough that the reranker’s candidate window could cover most of a persona’s evidence. Splitting a job into multiple queries sometimes surfaced generic passages about broad tasks such as documentation. Adding those results could crowd the top ranks with evidence that was relevant to a small part of a post and weak for the project as a whole. The predicted ten-point improvement from the combined decomposition, hybrid and reranking pipeline did not materialize. That result matters because a freelancer experiences the extra delay on every analysis, whether or not the proposal benefits. [Retrieval ablations and hypotheses](EVALUATION.md)

## The evidence gate made the gain invisible

The surprise came when I replaced V0 with V2 at the Fit Matcher’s retrieval boundary and compared the resulting bid decisions. On the 51 jobs in the gate check, zero decisions changed. The same 33 gold bid jobs passed with each pipeline. The evaluation records 37 jobs where the system retrieved labelled evidence that the gate could not count because the passage’s skill tags did not name the requirement. Retrieval had done its job. The decision layer applied a second, stricter definition of relevance. [Decision-gate analysis](../evals/results/retrieval-20261109-111100.json)

That rule is understandable. A proposal system should avoid claiming that someone has a skill based on a loose association. An exact tag gives the user a reason they can inspect. It also creates a maintenance obligation. Portfolio metadata must be specific enough to describe what the text already demonstrates. If an item explains that the freelancer isolated customer data in a database but omits the relevant skill tag, the passage may be useful to the writer and still count for nothing when the matcher scores that requirement. Adding a better embedding model will not resolve that mismatch.

I would test the gate independently next. One experiment would hold the retrieved passages constant and compare exact skill tags with requirement-level judgements that point to a specific supporting sentence. The dataset would need both supported matches and near misses. A passage that names a framework in a list does not necessarily demonstrate experience with it. A passage about the right technique may support the requirement even if it uses different words. I would measure false matches and missed matches, track which jobs change bid decisions, and inspect the evidence behind those changes. This isolates the risk of weakening the gate from the value of improving search.

## The same lesson applied to tools and approvals

The tool study showed that labels at an interface change what a model can do with the information it receives. On 40 synthetic requests per configuration, the fine-grained tools achieved 82.5 percent tool-selection accuracy and 80 percent argument accuracy. Rewritten descriptions achieved 92.5 percent and 90 percent, with more reported tokens per task. The coarse configuration used slightly fewer tokens than the fine-grained one and performed worse on both accuracy measures. Provider rejections are recorded separately alongside task totals. Better descriptions improved the observed decisions at that boundary, while simplifying the tool set did not deliver a useful trade in this run. [Tool study](../evals/results/tools-20261114-120333.json)

An approval boundary also needs its own evidence. A writer can put convincing text in a draft, but only a saved human decision can authorize the exact action. GigBid binds that review to a draft version, destination, quoted amount and dry-run Connects cost. A changed draft goes back through verification and compliance. Persisted state means the worker can come back after a restart and reconcile a previously attempted mock write. Those boundaries are testable without asking a model whether it followed instructions. [Bid and approval workflow](BID_WORKFLOW.md)

The local real-model smoke run repeated one proposal and reply scenario across 30 fresh accounts. It submitted 28 mock proposals and sent 29 mock replies. One proposal failed critique, another hit a rate limit, and one reply timed out during compliance. The seeded scam was skipped. The planted-instruction case reached human review and remained unsubmitted. This is useful repeatability evidence. It leaves important questions open about how often unfamiliar jobs will reach approval and how the deployment handles provider limits under reviewer traffic. [Smoke run](../evals/results/smoke-20261115-162627.json)

## What I would measure next

To make the results easier to interpret, I would record how far each job gets through the workflow. For each run, I would keep the evidence retrieved, the requirements that received support, the resulting bid decision and the final approval state. I would then report how many jobs reach each stage, using the original job count as the denominator. That makes a provider timeout visible alongside a policy skip or a missing citation, and it helps explain why a change that improves drafting may have little effect on the number of proposals a user is able to review.

The development results come from a labelled synthetic corpus. Historical instructor listings can populate the inbox, but they do not supply evidence labels, official GigSim outcomes or human ratings. I would keep the deployment’s retrieval configuration visible and rerun the relevant comparisons if the hosted configuration changes. I would also finish the matched comparison between the single ReAct agent, the prebuilt supervisor and the custom graph. The comparison needs the same jobs, model, tool permissions and execution budgets. The goal is to find out which failures each design prevents and what each prevention costs in latency and tokens. The rubric judge also needs the human calibration labels before its scores support a stronger quality claim. [Evaluation status](EVALUATION.md)

My main finding is that a better-ranked passage has value only if the next decision can use it. In GigBid, the strict skill gate made a measurable retrieval gain invisible to the bid decision. The tool experiment showed the reverse. Improving the wording at an interface changed selection accuracy even though the underlying operations were the same. Both observations point toward testing the handoff itself. A system can retrieve better evidence, pick the right tool and still fail at a later approval boundary. Measuring each handoff tells me where further work is likely to improve the freelancer’s experience.
